# ADR-051: The diagnostic places a learner; it is never an active task, and placement is reachability without mastery

*2026-10-08*

**the reported bug was one line of a gate reading the wrong fact.** `scheduler.Recommend` offered the diagnostic whenever `ConceptsMastered == 0 && AttemptedDays == 0` and `ApplyGoalResults` seeds placement as `PRACTICING`/`LEARNING` and stamps `LastAttempted` so the seed is a resumable candidate rather than an untouched row, so a learner who had just finished the diagnostic was offered it again, forever, and the profile rendered `Continue: diagnostic`. `diagnostic_completed` was stored on `students` and **nothing on the server read it**; the client inferred completion from local storage (`getUserInfo`) and from having displayed the last question, and `MeSchema` did not even parse the field the server sent. `RecommendInput.DiagnosticCompleted` is now the gate, read from `repo.GetStudent`, and `/api/auth/me` carries `diagnostic_completed` and `diagnostic_completed_at` (a real column on both stores, set idempotently so a backfilled flag shows no invented date). The client reads placement from the server; showing a question is not completing it. **Placement is reachability, not evidence, and that distinction is load-bearing.** A diagnostic-correct concept is seeded `PRACTICING`, and the scheduler's `prereqsMet` accepts only `MASTERED`/`DECAYING`, so the seed satisfied no successor and the frontier the learner was placed at was locked, placement was inert, and a completed diagnostic could yield *zero* eligible tasks. `concept_progress.placement_seeded` now marks a seeded row, `scheduler.ConceptSnapshot.Placement` carries it, and `prereqsMet` treats a placement-seeded prerequisite as satisfied. It is **not** mastery: `countsAsMastered`, `MasteryPct`, the quiz gate and XP never see it, `ApplyGoalResults` still writes no `MASTERED`, and ADR-008's "placement never destroys mastery" is untouched (only `UNSEEN` rows are seeded). The rejected alternative was seeding `MASTERED` from one answer, which is the "assessment writes mastery" ADR-050 chose against and violates ADR-038's six-answer floor. **Eligibility is one server answer, enforced where it counts.** `scheduler.EligibilityOf` derives `mastered`/`due_for_review`/`in_progress`/`unlocked`/`upcoming`/`locked` from the same `prereqsMet`/`effectiveState` the recommender and question scheduler use (ADR-042: no second rule), `Engine.EligibilityFor` renders it with prerequisite detail and `met` flags, and `/api/lessons/{id}/readiness` now carries `eligible`/`state`/`reason`/`prerequisites` beside the soft `ready/weak/missing` banner. **Amended Phase 0:** that banner now treats a **decayed** prerequisite as satisfied, matching the canonical gate, the response was telling two stories (`weak` banner, `eligible` verdict). Review routing is unaffected: the canonical `prerequisites[]` list still carries `due_for_review` states that the client routes to `/review`; only the advisory `weak` bucket changed. Eligibility, `prereqsMet`, and ADR-037 stand as before. The hard gate lands on `GET /api/lessons/{id}/practice` (403 `TOPIC_LOCKED` with `prerequisiteConceptIds`) and `POST /api/study/answer`, so a hand-typed `/learn?concept=` URL cannot start a locked topic either; the frontend's `PrerequisitePanel` explains the path and routes each prerequisite into `/learn` (or `/review` for decayed), never into the reference library (ADR-047). `/learn` reads `eligible` first and renders the panel instead of fetching questions the server would refuse. **The profile became a learning home, not an analytics page.** `RecommendedTaskList` renders the engine's set (`/api/next` primary + alternatives) as equal, actionable cards, server-owned badge/detail/cta/xp, no client ranking, where the old `NextUpSummary` committed to a single head; selecting a card asks the server for eligibility and then enters the one `/learn` loop, so a recommended concept and a manually chosen one converge. `NextUpSummary` and its test were deleted rather than left orphaned (the repo's orphan guard caught it). The order is `Where you are` → `Your learning` → `Choose what to learn` → `Needs attention` → `Activity` → analytics, and the completed diagnostic no longer appears as a CTA or a task. **Amended 2026-10-11, Activity moved to second, directly under a merged header** (`ProfileHeader` folds the stat strip and the position block into one card so MASTERED is named once). The report had become a wall of bordered boxes: the new order is Header → Activity → alerts → Your learning → How you're doing → Needs attention. The "What to do first" grid and Recently unlocked are gone (the header footer carries the diagnostic/plan actions, the task rows carry the rest), the task cards became compact two-line rows, and How you're doing and Needs attention collapsed to summary rows. **Amended 2026-10-11, the header compacted to short sentences and How you're doing returned to boxes.** The merged header still read as two blocks (avatar, LV tile, four stat tiles and a bar stacked on a big number, second bar and 3-column grid), so it now renders identity, reach, XP, streak, the mastery breakdown and Start-here in plain sentences; TOTAL XP and the WEEKLY link were cut, and `PositionBlock` was deleted with its tests folded into the header's. The efficacy row went back to the four boxed cards the brief asked for. `GET /api/curriculum/domains` and `GET /api/curriculum/domains/{id}` are the read-only curriculum source (per-domain counts and per-topic `state`/`depth`, derived through `EligibilityOf`), and `/domains` became the picker: server states, text labels that survive without color, `Learn` for available topics, `View prerequisite path` for locked ones. Domain ordering/labels stay presentation-only in `lib/graphDomains.ts`; the corpus stays the one curriculum definition (ADR-001). Verification: Go suite including new placement/eligibility/curriculum/HTTP-gate tests, 661 web unit tests, `tsc`, `next build`, `go vet`, oxlint clean on the changed files, and `check_docs.py` / `check_ste.py` / `counts.py --check`.
