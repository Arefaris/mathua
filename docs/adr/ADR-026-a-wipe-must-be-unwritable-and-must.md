# ADR-026: A wipe must be unwritable, and must not lie about why (2026-10-03) — amends ADR-022

A wipe must be unwritable, and must not lie about why (2026-10-03) — amends ADR-022: reset and delete only wiped the database, but `diagSessions` and `quizSessions` live in `Server` memory and the janitor swept them by age after an hour. A learner who reset and then reopened the tab they had left mid-diagnostic got their record back, because `handleGoalDiagnosticAnswer` re-inserts the attempt (`EnsureSession` + `RecordAttempt`) and `handleQuizAnswer` writes `concept_progress` and XP via `SubmitQuizAnswer`. Worse on Postgres: SQLite's `sessions` FK made `EnsureSession` fail and so accidentally shielded deletion, but Postgres omits those FKs (ADR-012), so **delete left real `attempts` rows for an identity that no longer exists**. Both handlers now call `Server.dropStudentLiveSessions` after the engine succeeds, so a stale answer is refused with 404 instead of rewriting the wipe; the age janitor stays for genuinely abandoned tabs. Second half: both handlers collapsed *every* engine error into `400 "confirmation phrase does not match"`, so a database refusal reached the learner as "you typed the wrong words" — unsendable advice, since the phrase was correct. `ErrResetPhraseMismatch`/`ErrDeletePhraseMismatch` are exported and matched with `errors.Is`; a real fault is now 500 and logged. Client-side, `resetAccount`/`deleteAccount` used `res.text()`, putting a literal `{"error":"…"}` in the danger zone; both now use the existing `throwWithResponse`. Also: `DeleteAccount` tracked the password requirement as a boolean, so a failed `getMe()` hid the field and the server's 401 `current password is required` had no input to satisfy — it is a tri-state now, showing the field but not requiring it when unknown, and the field's accessible name is distinct from the change-password field on the same page. Root cause of all of it was coverage: `POST /api/account/reset` had **no HTTP-level test at all**, and `ResetProgress` had **no Postgres test** (`TestDeleteAccount_RemovesEveryOwnedRow` is excluded from CI by the `-run TestParity` filter). `ResetProgress` now runs against both stores. Unrelated but found en route: `TestDeleteAccount_RemovesEveryOwnedRow` leaked the `Next` row that claims the freed address, so any reused DSN failed on `uidx_students_email` — invisible in CI, which gets a fresh database.
