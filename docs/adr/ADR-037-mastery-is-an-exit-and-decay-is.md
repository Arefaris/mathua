# ADR-037: Mastery is an exit, and decay is not a return to class

*2026-10-04*

the report was "stop sending me through tutorials for things I already know", and the audit found the opposite rule in four places. **The tutorial purgatory was one predicate.** The shelf's only status filter asked `status === 'MASTERED'` (`lib/nextUp.ts`), while the server reports a concept whose review has gone stale as `DECAYING` and never as `MASTERED` — `Engine.GetProgress` applies decay at read time and the DB stores `MASTERED` forever. So a fortnight's break read as *not started*, the concept re-entered as a `resume` item, and `/learn` opened with its worked example unconditionally (it has no notion of the lesson having been seen before) — three KP sections before the first question. `buildCandidates` now asks `countsAsMastered`. `/study` had the same disease at its other end: `headCid` fell back to `learnTargets[0]`, so a **fully-mastered lesson presented an already-demonstrated concept as its primary call to action**. Retrieval practice is reclassified rather than dropped — `/review` was already the one clean route (problems first, no lesson fetch, no `/learn` exit), and it was *under*-linked, because the shelf collapsed all reviews into one count card and so steered decayed concepts to `/learn` instead. **`lib/graphStatus.ts` was the fifth copy of the mastery predicate and had already drifted**: it knew MASTERED/PRACTICING/LEARNING but not DECAYING, so a decayed concept matched nothing, rendered as `unseen` with no bar, and — missing from its `mastered` set — **relocked everything downstream**. That is the failure `lib/progress.ts` was extracted to prevent, its own comment predicting it; and it is exactly what ADR-024 ruled out when it made `prereqMet` accept DECAYING. It now asks `lib/progress.ts` both questions. On the graph decay is **color only**: same full bar, byte-identical geometry, no second bar, no pattern, no badge, no shorter fill — `decaying` takes a deeper amber than `learning` precisely because color is the only channel. **The bar never meant attainment.** It was `streak / threshold`, and the engine resets the streak to 1 on every tier advance (`if newStatus != oldStatus && gr.Correct`), so it hit 100% and fell to ~10% three times on the way up — measured at answer 10 for a threshold-10 concept: 0.9 then 0.1. Attainment is now the tier, not the counter: each transition is worth a third, progress within the tier fills the rest, which is monotonic across an advance (LEARNING at 9/10 reads 63%; the same instant as PRACTICING at 1/10 reads 70%). `mastery.MasteryPct` lives beside `Machine.Next`, `GET /api/progress` serves it, and the graph reads it instead of dividing by a *bundled* threshold that drifts whenever the corpus is rebuilt. `engine.MasteryPct` and `MasteryBand` had no callers outside their own test and were deleted; the old function also dropped DECAYING to 0.8, i.e. decay as a shorter bar, which reads as losing the competence. **`decayDays` was written four times and one copy disagreed** — 14 in the engine, a bare 14 twice in the scheduler, and **30** in the workload estimator, so a plan promised a review cadence the app would not honour, on the path the deadline is computed from. Now `mastery.DecayDays`. **Progress was cached for the life of the tab.** `/graph`'s helper was named `once` with its map named `inflight`, so in-flight dedup was the intent; it deleted only on rejection, so a successful response was reused for the session — and answering is the one action that makes progress wrong, with no polling or revalidation anywhere to correct it. `/study` had the identical bug and worse, because its payload carries `progress[cid].status` for every concept chip. Both now dedupe in flight only; `health` and `GET /api/graph` are immutable and keep a session cache. **One prior decision reversed:** a test asserted DECAYING *lowers* the mastered count, "which is the point of reporting it" — a sound instinct, but it made Profile disagree with the graph, where a decayed concept has a full bar. `mastered` now means "demonstrated and not yet stale" and decay is its own number, `dueForReview`, shown on Profile. **Deferred, and stated rather than faked:** §4 asks for evidence including retrieval *after spacing*, and the data model cannot express it. `concept_progress` has fourteen columns and none records when the current tier was attained — `mastered_at` is set once for the final tier, and `last_reviewed` refreshes on any answer meeting the threshold and is already the decay clock, so it cannot be overloaded. Closing this needs a persisted `tier_attained_at` and a migration on both stores, which is an architecture change rather than a threshold, and the brief asks for the limitation to be reported instead. `sm2_repetitions` does grow with each successful review, so long-term retirement falls out of pushing `next_review_due` out — no `RETIRED` state is needed.
