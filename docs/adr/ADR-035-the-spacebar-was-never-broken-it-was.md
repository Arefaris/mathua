# ADR-035: The spacebar was never broken, it was empty

*2026-10-04*

the report was "the space button is not working" in the `abc` area. MathLive's own `alphabetic` layout, the one appended to every mode and reachable from the keypad toolbar, declares `{ label: " ", width: 1.5 }`: a label and a width and **no `command`, `insert`, `latex` or `key`**. `executeKeycapCommand` resolves `command` → `insert` → `key` → `latex` → `typedText(label)`, so it falls through to `typedText(" ")`, which reaches the `[Space]` handler, which inserts `options.mathModeSpace` **only when it is non-empty** and otherwise just calls `moveAfterParent()`. `mathModeSpace` defaults to `""`, so the caret moved and nothing was inserted. Upstream defect, not a Mathua regression. Three generator answer formats need a real space (`Q R`, `a sqrt(b)`, `P=[[...]] D=[[...]]`), so it was not cosmetic. Three things had to be measured rather than read. **(1) The documented attribute does nothing.** `math-mode-space=","` lands in the DOM and `placeholder` and `class` are both honoured from React-rendered attributes, but `mathModeSpace` stays `""` and the key stays inert; `el.mathModeSpace` and `setOptions` both work. An attribute that is silently ignored is worse than none, so the attribute is gone and the property is set in an effect. **(2) The obvious keycap fix is ADR-029 again.** `{ label: ' ' }` works (it maps to `[Space]`) but renders blank, which is half of why the key read as broken; the visible `label: '␣'` **types the glyph `␣` into the field**, because with no payload beside it the label is typed. So `{ label: '␣', aside: 'space', latex: '\\,' }`, payload stated, face visible. `\\,` because TeX discards literal spaces in math mode, and it is the proven round trip: the corpus holds `expression 5 R 3 <- 5\\ R\\ 3` → plain `5 R 3`, which grades. **(3) The keypad's width budget is keycap-widths, and it is viewport-dependent**, MathLive renders every key at 45px regardless of row content (93px for `width: 2`), so the ceiling is `units × 45` against the panel: 8 units at 412px, **6 at 320px**. My first attempt put a width-2 spacebar on every grid and pushed ARITHMETIC's bottom row from 6 units to 8, which **broke the 320px audit that had been passing**; that was caught by running `mobile-320`, and reverted. Consequence: the space key is on the arithmetic grid only, the one row with a spare unit, and the mode that needs it (`Q R` and mixed numbers), and every other mode reaches the working `alphabetic` bar. Two 9-unit rows in `algebra` and `geometry` were also fixed (one keycap moved up each), because 9 units renders at **42px**, under the floor; the existing audit could not see it because it only ever measures `ARITHMETIC`. New unit test asserts ≤8 units for all five modes. **Open, and not fixed here:** thirteen rows across four modes exceed the 6-unit 320px ceiling, so the 44px floor holds at 412px and not at 320px; the e2e audit passes at 320px only because `ARITHMETIC` is the one mode that fits. That needs the eight-keycap rows split, which is a redesign. Deferred: a first-class space key on the non-arithmetic grids.
