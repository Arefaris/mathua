# ADR-031: The loading state is the editor that always works, not a spacer

*2026-10-03*

the reported "I have to type Check Answer multiple times for it to work" was a silent no-input window. Between the answer UI appearing and MathLive being usable, the Suspense fallback was `<div className="h-12" aria-hidden />` — the right size in the right place, so a tap looked like it landed on an answer field and then vanished, and every keystroke went nowhere; Check Answer was correctly but unhelpfully disabled because no answer existed, so the learner tapped, typed, tapped Check, and repeated. Measured with the new `e2e/answer-diagnosis.spec.ts` (`performance.now()` throughout, one clock): the window is **322ms** with the chunk cached and **3116ms** with a 3s chunk delay — seconds on a real phone connection. Hypotheses 2-4 are **not** implicated: once the editor is up, `input → React state` is **2-7ms** and `first tap → API response` is **12-14ms** on all three profiles. So the fix is not cosmetic — `PlainAnswerInput` is now shared by the loading state *and* the chunk-failure fallback, so the learner can answer during the window instead of repeating themselves; typed text is reported as the LaTeX too, so `MathLiveField` adopts it on mount. Two measurement traps are worth keeping: **CDP network throttling cannot reach the MathLive chunk in this harness** (it reported `transferSize: 0` and finished in 39ms under 4 Mbps while main chunks took 1100-1400ms — served from Chromium's memory cache), so a first pass concluded "the network does not matter" and produced a window that never moved; and a page-level `route` never fired for the same reason, giving four mutually inconsistent numbers. The chunk delay now resolves its target by scanning the build output for MathLive's markers, routes at context level, and **counts its own interceptions** (`delayApplied`) so a run where it did not apply cannot contribute a number. A consequence of the fix worth naming: the loading input shares the editor's placeholder, so an unqualified "answer field" query started returning the transient control — the same swallowed-tap failure, relocated into the tests. It is marked `data-mathua-loading` and `answerField()` excludes it.

**Amended 2026-10-05 — the residual `mobile.spec.ts:349` failure was diagnosed as a value-propagation race and that diagnosis was wrong; it is synthetic keystrokes being swallowed by the virtual keypad, and it is not rare.** `4b8adcd` added `expect(submit).toBeEnabled()` because the click was landing on a disabled button, which was a real fix, then attributed what remained to machine load on the strength of a probe that logged `activeElement` and the field's LaTeX across twelve cycles and found typing reaching the host every time. **That probe cannot have observed this**, because on a coarse-pointer profile `MathLiveField` opens the virtual keypad on focus and at 320px the open keypad swallows `page.keyboard.type` — the same fact `mobile-math.spec.ts` already records at its own call site, which is why every touch test there taps keycaps. Measured: on `mobile-320`, typing fails **4 of 6 runs** with an idle single worker, and 3 of 3 in CI; `mobile-chromium` passed throughout. So it is a high-frequency failure that happened to look intermittent locally, not a load-sensitive one, and "one full suite run in three" understated it. The failure mode is ADR-036's again: the probe was run where the keypad does not exist, so the one thing that mattered was invisible to it. `e2e/helpers/answer.ts:enterAnswer` now picks the input method from `(pointer: coarse)` — types with a physical keyboard, taps keycaps without one — and `typeAnswer`'s doc comment names the trap so the next call site cannot repeat it. 8 of 8 passes afterwards, none near the 20s timeout. Also worth recording: the `chromium` project's `testIgnore` excludes `mobile*.spec.ts`, so this double-submit test has **no desktop coverage at all** and its typing branch is therefore never exercised by it.
