# ADR-049: Admin V2 turns administration from a localhost tool into a deployed, permissioned one

*2026-10-08*

**The problem was not the features, it was that the only way to run an administrative action was to own the machine.** V1 had roles, a transactional audit log and a last-admin guard and none of it helped a second trusted contributor, because adding one meant editing source or the environment. The change is a permission model, an invitation workflow and a moderation queue, and the load-bearing part is that a route names a *permission* while the middleware reads a *role*: the two are different words and the gap between them is where escalation lives. **Four roles, ordered least to most:** `student`, `moderator`, `admin`, `owner`. V1's `admin` was full control, so the migration moves each V1 `admin` to `owner`, the move that preserves capability, where leaving the value as `admin` would have silently removed the power to manage staff. The invariant moved up with it: V1 guarded the last *admin*, and nothing but an owner can create an owner, so the last *owner* is the one the system may never empty. It stays inside the UPDATE for the reason ADR-048 gave, a count read before a write is a race two owners demoting each other both win, and `ErrLastOwner` is its own sentinel rather than a reuse of `ErrLastAdmin`, because the two roles are no longer the same fact. **`internal/admin` is the model, as data.** Each role maps to a set of permissions and `CanAssign` applies three rules: you cannot grant above your own rank, you cannot act on a peer or superior unless you are an owner, and granting `owner` needs a permission only an owner holds. It is a package rather than scattered checks because a matrix spread across handlers is a matrix nobody can review, and its failure mode is a route that forgot a check rather than a route that got one wrong. `TestCanAssign` states the rules as a table; `TestAssignableRolesMatchCanAssign` pins the picker to the check, because a role the client offers and the server refuses is a broken control and a role the server allows and the client hides is a feature nobody can reach. **The two trust models were the thing to end, not to keep.** V1 ran role administration and a shared-`ADMIN_PASSWORD` content triage side by side under `/admin`, and ADR-048 defended the separation because the two genuinely were different. They were also two administrative systems, and a shared password cannot say which person used it. V2 removes the triage endpoints, the login and the session kind, and folds moderation into the role model at `/api/admin/reports`, so there is one mechanism and one audit trail. **Reported content is a moderation record, not a queue item.** Resolving sets the status, the moderator's reason, who decided and when, and writes the audit row in the same transaction; the row is never deleted, so "what was reported and what we decided" survives. The V1 statuses `confirmed`/`fixed` migrate to `reviewing`/`resolved`, the same states under honest names. **Invitations are how a contributor arrives, and they are deliberately boring.** An owner or admin creates one for an email and a role; the server generates 32 random bytes, returns them once, and stores only the SHA-256 hash, the same construction as the password-reset tokens, because a second scheme for the same job is how one of them ends up weaker and nobody notices which. Acceptance is one transaction that burns the token, grants the role and audits it, so there is no state in which someone holds a staff role with no record of how; it is bound to the invited address, checked before the burn, so possessing the token is not enough; and every failure, unknown, expired, revoked, reused, wrong address, answers the same, so a prober learns nothing. `ConsumeAdminInvitation` reusing the single-use-token pattern is the point: this is a solved problem in this codebase and a second implementation would be a second set of bugs. **The UI filters and the server decides, and the code says so where a reader would assume otherwise.** `AdminNav` shows a section only when `/api/admin/me` reports the permission, `useAdminMe` is labeled a convenience in its own comment, and every route re-checks server-side, the same discipline as ADR-048's `AdminNav`, extended from one boolean to a matrix. `/api/admin/me` exists so the client can render honestly without the server trusting it; the alternative, a client that guesses its own capability, is a client that shows a button the API will refuse. **Content is inspection, not a CMS.** The corpus is code-adjacent data with no safe write path, and the brief's instruction was explicit: provide inspection rather than invent a fragile editor, so `/admin/content` reads concepts and their prerequisites and stops there. **Migration and scope:** the V1 admin tests were rewritten to the owner invariant rather than deleted, `TestTriagePasswordDoesNotGrantRoleAdministration` was removed with the triage it guarded, and the CLI now grants `owner` because the first promotion must be able to create the rest. Verification: the Go suite across storage, server and the new `internal/admin` package including a full authorization table (401/403 per role, self-escalation, peer demotion, invitation lifecycle, moderation audit), 665 web unit tests, 231 Playwright at CI settings with a rewritten `admin.spec.ts` covering the role picker and the moderation queue, `tsc`, ESLint clean and `oxlint` unchanged at 82, and `check_docs.py` / `check_ste.py`.
