# ADR-048: Administration is a role on the account, and it is re-read on every request

*2026-10-08*

**V1, and the whole of it is the boundary.** Two roles (`student`, `admin`) on `students.role`, `NOT NULL DEFAULT 'student'`, so every existing account migrates to a learner — the only safe direction, because a pre-role database holds no evidence about who was administering anything, since nothing in it could. The role is **not** derived from XP, mastery, level, progress, email domain or anything the client sends. **The load-bearing decision is where the role is read.** `requireAdmin` authenticates, identifies, then queries `GetStudentRole` on **every** request rather than trusting a claim in the token, because a role baked into a JWT keeps granting admin until the token expires: demoting an administrator would leave them able to promote themselves back for the life of their session, which is the one failure this feature exists to prevent. `TestLastAdminDemotionTakesEffectImmediately` is that argument as executable code, and it is the reason the field is not in the token. **The last-admin rule lives inside the UPDATE, not before it.** `DemoteAdminSafely` is one statement whose WHERE clause contains `(SELECT COUNT(*) FROM students WHERE role='admin') > 1`; a read of the count followed by a write is a race that two administrators demoting each other both win, and the system reaches zero through the very feature meant to stop it. `TestConcurrentDemotionsCannotReachZeroAdmins` runs the race twenty times against a file-backed store. **Getting that test to tell the truth took a fix that is worth more than the test.** It first failed with `admins = 0` — which looked like the guard not working. It was the harness: `NewSQLiteStore(":memory:")` combined with `SetMaxOpenConns(8)` means **each connection opens its own database**, so the second concurrent statement got an empty one and reported `no such table: students`. Sequentially the pool reuses its one idle connection, so every other test passes, which is exactly what makes it hard to find. The trap is now documented in `NewSQLiteStore` next to the pool size, because the next person to write a concurrent test will hit it and will not know to distrust the number. **`Role` is not a field on `storage.Student`, and that is the safer shape.** Every existing read of `Student` selects a fixed column list in two stores, so a column there meant editing roughly twenty query strings to keep them in sync — and a missed one is a scan error at runtime in whichever endpoint nobody was testing. The worse reason is the default: a privilege field that reads `student` when it has not been loaded is indistinguishable from a correct conclusion, so forgetting to populate it would be silent. `GetStudentRole` is the only way to learn a role, and it returns `student` for a missing row so a deleted id fails the request rather than the middleware. **`NormalizeRole` fails closed and `ParseRole` fails loudly, and both are needed.** The first maps anything unrecognised — a future role, a typo, a hand-edited cell — to `student`, so an unknown value is never more privilege than a known one. The second rejects it outright, and assignment goes through it, because coercing `"Admin"` to `student` would leave the 200 response and the stored row disagreeing, which is the exact quiet disagreement ADR-041 kept finding. **`AdminUser` exists because `Student` cannot be the thing an admin list returns.** It has no field for a password hash, a share token or learning state, so "the admin list leaks nothing sensitive" is a property of a type rather than a promise about a query, and adding a field to it becomes a deliberate act. Both snapshots in an audit row are built from it, which is why a credential cannot reach the log. The user's own `/profile` page had **redeclared** `UserInfo` locally and now imports it — ADR-043's duplicate-schema failure in miniature, and exactly what happened when `role` arrived. **The audit log has no foreign key on `actor_id`, deliberately:** a trail deleted along with the account it records is not a trail, so the actor is kept as text. There is no update and no delete method on either store and no route for one, which makes "not editable" a property rather than a promise about the UI; the page has no text input at all. **The gap this ADR originally named is closed: the mutation and the audit insert are one transaction.** `SetRoleAudited(actorID, studentID, role)` opens a transaction, reads the before-snapshot inside it, applies the mutation, reads the after-snapshot inside it, writes the event, and commits — so a failing insert rolls the role back instead of orphaning it. **The before-snapshot had to move inside the transaction too**, which is the part that is easy to miss: a snapshot read from the pool would describe committed state rather than the state being changed, and the audit row would then describe something the transaction never did. That is why `adminQueryer` exists — the projection read takes an interface that the pool and a `*sql.Tx` both satisfy, so there is still exactly one query in the package that can produce an `AdminUser`, and the before and after snapshots are guaranteed to be the same projection the list returns. `TestFailedAuditInsertRollsBackPromotion` and its demotion twin prove the rollback by installing a `BEFORE INSERT` trigger on `admin_audit` that calls `RAISE(ABORT)`. A trigger rather than a stubbed repository is the honest way to make the insert fail: a mock would let the code pass a test and still leave a real deployment with an unaudited role change. **That test was run against a deliberately broken build** — commit the mutation, then insert — and it fails with the message "the mutation was not rolled back", so it measures the property instead of restating it. **A no-op became its own sentinel** (`ErrRoleUnchanged`) rather than a success with a flag, because the audit write is now inside the transaction and "nothing happened" has to be a real outcome rather than a return value a caller can forget to check. The handler is one call and four error cases, and there is no longer any code path in it that can change a role without recording it. **The CLI now shares that one primitive, which reverses a decision this ADR originally recorded.** It said `SetStudentRole` stays separate on purpose: the operator's path, able to make the first promotion, unreachable from the network. The reasoning was sound and it was still wrong, because "separate" had quietly become a second way to change a role — one that writes no audit row, so the ledger could not answer the only question it exists to answer. The command now calls `SetRoleAudited` with `adminActorCLI = "cli"`, and the separate store method is gone. The bootstrap argument is untouched and was never the reason for the split: shell access can still make the first promotion, it still refuses an account that does not exist, and it is still not on the network. What is gone is the second code path. A second writer of `students.role` is a hole in an invariant, and "it is only the operator" describes who, not whether. **A no-op is not an event.** Promoting an existing administrator returns `changed: false` and writes nothing: an audit row for a change that did not occur is noise, and the log's value is that every row is a fact. **The bootstrap is a shell command, and every alternative was worse.** An HTTP endpoint means anyone who can reach the server can ask to become an administrator, which is not a bootstrap but an open door; a role in the signup body means a client picks its own privilege; an env var naming the first admin needs a row to point at and silently stops working once there is one. Shell access already implies full control of the deployment, so it is the right place for the decision that someone should have it. The command **refuses to create an account** — promoting an address nobody signed up for would make the operator's guess into an administrator with no password. **`/admin` now holds two unrelated trust models and the code says so where a reader would assume otherwise.** `/admin/reports` is content triage behind the operator's shared `ADMIN_PASSWORD` and confers **no account identity**; `/admin/users` and `/admin/audit` are account administration behind a role. `TestTriagePasswordDoesNotGrantRoleAdministration` pins the separation in both directions — the triage token answers **401** there rather than 403, because it is a `server_sessions` row and not a signed learner credential, so it fails authentication before a role is ever consulted. That is a stronger separation than "the same identity, fewer rights", and it is worth naming so nobody later "simplifies" the two into one. **`AdminNav` is a convenience and is documented as one**: a learner who types `/admin/users` reaches the page, sees why it is empty, and is refused by the API. The pages render for anyone, deliberately — a page that renders nothing for the wrong caller looks broken rather than refused. **A privileged action is confirmed, and the dialog starts on Cancel.** `ConfirmDialog` opens with focus on the button that does nothing, so a stray Enter cannot promote anyone, and Escape, the backdrop and Cancel all dismiss without a request. The buttons are named `Make administrator` and `Remove administrator` and the dialog names the account, because the row that was clicked is not proof that the person meant the account they are looking at. Two errors were kept apart on purpose: the list's own failure and the mutation's refusal are different messages, and an early version had one slot for both, so the server's `cannot demote the last administrator` was replaced by nothing the moment the page refreshed the list behind it. **The deployed surface was broken in a way no unit test could see.** The static export writes `/admin.html` *and* an `/admin/` directory, and `nextStaticFS` probed a requested path with `os.Stat` and, finding it, served the index template — so on the real binary `/admin` answered `301` to `/admin/`, and `/admin/` served a generated directory listing instead of the application. Every route returned 200 and every test passed, because the defect is in the handler that serves files rather than in any page. It is now `!st.IsDir()` in `cmd/mathua/main.go`, with `cmd/mathua/staticfs_test.go` asserting no response body contains a `<pre>` listing. **The first browser-level test found a second bug, in the product this one was written for.** `/profile`'s loading and error branches passed `isAdmin` to the sidebar and its main branch did not, so the Admin entry appeared and then disappeared once scores arrived. `test/app-sidebar.test.tsx` covers the component's prop; the wiring is only observable in a browser, which is what `e2e/admin.spec.ts` is for. **Five counts and no charts.** Accounts, administrators, concepts, domains, stored questions: the numbers an operator can act on without another tool, read live on each visit and never precomputed into a dashboard table, because a number that must be refreshed is a number that will be stale in the screenshot someone argues from. Concepts and domains come from `Engine.CorpusSize` rather than a query — the corpus *is* what Mathua teaches, so counting rows would report what has been visited. Zero administrators raises an alarm naming `mathua admin promote`, because at zero the surface is closed *including the route that would fix it*. **Scope held:** no curriculum editing, no question CMS, no publishing, no bulk operations, no permission matrix, no editor for XP or mastery or attempts — learning state is the learning system's record, and an administrator with a text box in front of it will eventually use it. `test/learningPath.test.ts` and `test/adminSurface.test.tsx` came out of the same discipline: assert the property, not the layout, and strip comments first so the reasoning can live in the code without tripping the guard. Verification: 47 Go authorization cases, a new storage suite, 659 web unit tests, 229 Playwright across three viewports including a new administrator-management spec, `tsc`, ESLint, `oxlint` unchanged at 82, and `check_docs.py` / `check_ste.py`.
