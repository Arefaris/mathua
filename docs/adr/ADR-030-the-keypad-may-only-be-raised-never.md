# ADR-030: The keypad may only be raised, never lowered

*2026-10-03*

Mathua hid the virtual keyboard from a capture-phase `pointerdown` listener on `document`, any tap outside the field dismissed it. Removed. MathLive raises the keypad from exactly one place, a document `focusin` listener that calls `show()` after 300ms gated on `policy === 'auto' && hasEditableContent`, and there is **no re-show path**: hiding the panel while the field still holds focus leaves no way back, because no focus transition means no `focusin`, so tapping the field again does nothing. That is the reported "the keyboard doesn't always appear on every input", the learner taps a non-focusable area, the keypad vanishes, and the field is still focused. iOS Safari frequently does not blur on a non-focusable tap, so it reproduced on a phone while being invisible in Chromium, which is why it survived the original suite. MathLive already hides the keypad itself from a `focusout` listener when focus genuinely leaves, so the outside-tap listener was both redundant and harmful; Mathua now hides it in exactly one place, a focused field unmounting, and `MathLiveField`'s `pointerdown` handler is the recovery path. Because `show()` only dispatches a message it is safe to call when the panel is already up. The regression test spies on `mathVirtualKeyboard.hide` and asserts Mathua never calls it on an outside tap, chosen because `hide()` is a no-op under Chromium, so asserting the resulting visibility would pass vacuously; the *recovery* behavior still needs a real-device check. Also fixed in the same file: the Enter keydown listener was registered **twice** (`el.addEventListener('keydown', onKeyDown)` twice, one `removeEventListener` in cleanup), so `onSubmit` fired twice per Enter.
