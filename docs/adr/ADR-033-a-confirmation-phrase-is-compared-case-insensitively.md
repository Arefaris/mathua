# ADR-033: A confirmation phrase is compared case-insensitively, because phones capitalise it

*2026-10-03*

the reported "the reset my progress button is not working" was `type="text"` with no `autoCapitalize`, so Safari upper-cases the first letter as you type and Android keyboards autocorrect, `reset my progress` arrives as `Reset my progress`. Both the client comparison and `Engine.ResetAccountProgress` were exact, so the button stayed disabled forever on a phone, and had it somehow submitted, the server answered "confirmation phrase does not match": telling someone who had typed exactly what the label asked for that they had **mistyped it**. Chromium does not auto-capitalise, which is why 513 unit tests and the whole e2e suite were green throughout. Both inputs (`DangerZone.tsx`, `DeleteAccount.tsx`) now carry `autoCapitalize="none" autoCorrect="off" spellCheck={false}`, both comparisons use `strings.EqualFold`/`toLowerCase` on the trimmed phrase, and both send the canonical phrase so the server's gate compares like with like. `TestPhraseMatches_CasingAndWhitespace` pins it, including that `delete my account` still does **not** unlock a reset, the two phrases stay separate values precisely so a reset confirmation can never authorize a deletion. Second half, and the reason it hid: a disabled button with no explanation is indistinguishable from a broken one, so both panels now show a `role="status"` line saying the phrase does not match once something has been typed. The phrase confirms intent; it is not a secret, and casing says nothing about deliberateness.
