# ADR-029: A keycap's `latex` is an insert, not a command

*2026-10-03*

backspace typed the literal text `[backspace]` and the zero key typed `[0]`, in **all five** layouts. Declared as `{ latex: '[backspace]' }`, which reads like a command. In MathLive 0.111.0 `executeKeycapCommand` resolves `command` → `insert` → `key` → **`latex` (run as an insert)** → `typedText(label)` and `normalizeKeycap` merges the library's own `KEYCAP_SHORTCUTS` only for a bare-string keycap or one naming a shortcut in `label`/`key`. So those two matched no shortcut *and* fell through to the insert branch. `KEYCAP_SHORTCUTS["[backspace]"]` carries `command: "performWithFeedback(deleteBackward)"` and `["[0]"]` carries `latex: "0"`; neither was consulted. Fixed by naming the shortcut in `label`, which is what MathLive's own layouts do. The trap behind it is worse: **`renderKeycap` adds `MLK__keycap` only when the class lacks `separator`/`action`/`shift`/`fnbutton`/`bigfnbutton`**, so backspace, the caret arrows, the dismiss key and every separator render without it, and every selector in the suite, including the 44px touch-target audit, used `.MLK__keycap`. That audit had been measuring only the keys that worked and passing clean over a keypad whose delete key typed its own name. `e2e/helpers/answer.ts` now has `keycaps()` (visible row children) and `glyphKeycap()`, and the audit asserts it reached the delete and caret keys so "no undersized keycaps" cannot revert to "no keycaps measured". `test/keyboards.test.ts` fails on any bracketed token in a keycap `latex`. Two e2e tests assert `answerLatex`, and both were confirmed to fail against the unfixed layouts before being accepted. A process note: `npx playwright` serves the prebuilt `out/`, so an e2e run against an edited component silently tests the *old* build unless `next build` is re-run first, which is how the first attempt "passed" a fix that had not been compiled.
