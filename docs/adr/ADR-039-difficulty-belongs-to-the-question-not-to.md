# ADR-039: Difficulty belongs to the question, not to the host that graded it

*2026-10-05*

ADR-038 left a hole it could not see and it was a correctness bug rather than a design gap. **The number is the argument:** `BuildEvidence` set `difficultyTerm = 1.0` when an attempt carried no difficulty, with the comment "the term is dropped entirely rather than assumed, so old attempts are neither rewarded nor punished for it". Dropping a *multiplier* means multiplying by 1.0, the top of the range, so a missing value was credited as *the hardest question the engine could have asked*. It was not cosmetic: at 50% accuracy the unknown-difficulty score was **0.65 and cleared `MasteryThreshold`, while the same attempts at difficulty 0.6 scored 0.57 and did not.** A learner could pass the mastery bar on one surface and fail it on another for identical answers. A pre-existing test named `TestBuildEvidence_UnknownDifficultyIsDroppedNotZeroed` asserted `score == 1.0`, so the wrong behavior was pinned by a name that described it accurately and believed it correct, the same failure mode as ADR-035's keycap that typed its own name, one layer up. **Two causes, one symptom.** (1) *Plumbing:* difficulty went **into** `GeneratorContext` and stopped there, `generator.Problem` did not carry it back out, so every surface that generated a question and later graded it had to thread the value by hand, and two of three hosts did not. `SubmitAnswer` read it off `activeSession`; `submitAnswerWithTask` (which serves **both** the Learn loop and quizzes) passed a literal `0`; and the diagnostic recorded its attempt row directly in `server.go` with no difficulty at all. So **the main Learn loop was the host with no difficulty**, not the quiz, the opposite of where this was reported from. `Problem.Difficulty *float64` is now stamped by `Registry.GenerateContext`/`BatchGenerateContext`, which makes it structurally impossible to generate a question without its difficulty; `engine.Anchor` carries it for study, because the anchor is already the durable "what was served" record and is authoritative over the expected answer for the same reason; quiz reads `sess.LastProblem.Difficulty`; the diagnostic stamps it on the attempt row it writes. The chain is the one CONTEXT intended: generation → question metadata → grading → `gradedAttempt` → `applyGradedAttempt` → mastery. (2) *Scoring:* unknown is credited at `mastery.NeutralDifficulty = 0.55`, which is **not chosen**, it is what `difficultyFromWeakness` serves when it has no information about the learner (weakness defaults to 0.5, so `0.3 + 0.5 × 0.5`), and `TestNeutralDifficultyMatchesEngineDefault` fails if the serving side and the scoring side ever drift apart. `gradedAttempt.difficulty` became `*float64` so "unknown" is a value the caller must choose rather than a `0` reinterpreted downstream; that overloading is precisely what hid the bug. **What this is not:** `applyGradedAttempt` does not guess or re-derive difficulty, recomputing from the learner's *current* weakness would credit an attempt with the difficulty a **future** question would get, which is a different claim from the one they answered, so the quiz parameter is passed from the served problem instead. `TestStudyAndQuizProduceEquivalentMasteryEvidence` drives both hosts with the same questions, outcomes and difficulty and requires the persisted rows **and** the assembled evidence score to match; `TestUnknownDifficultyIsNotMoreGenerousThanKnown` and `TestUnknownDifficultyHostIsNotMoreGenerous` assert the property directly. All three were confirmed to fail against the pre-fix shape, so none of them is a guard that passes vacuously. **Mastery and retention stay separate, and this change is what makes that safe to assert:** `BuildEvidence` takes only attempts and the concept's thresholds, no clock, no "last reviewed" input, so `TestEvidenceHasNoSpacingTerm` can show evidence scores identically regardless of age, and `TestMasteryIsNeverLostToBadEvidence` shows six consecutive misses cannot un-learn a mastered concept. A learner who demonstrated a year ago demonstrated what they demonstrated then; whether they still can it is the deferred `tier_attained_at` question, and `MasteryPct` keeps decay as color on a full bar so it never reads as loss of attainment. `questions.difficulty` is `NOT NULL DEFAULT 0.5`, so curated rows contribute a real value too, no third "unknown" population was left behind. **Deferred, and stated rather than faked:** `web/next-app/lib/progression.ts:masteryEstimate` is a **second** model and does not match this one, it weights difficulty per attempt rather than by the mean of the correct attempts, uses a fixed 60s time threshold rather than the concept's own, and has no unknown-difficulty case at all (`difficulty: number` is required), which is why this change creates no *new* browser/server divergence. It still fed `LearnStepper`'s `advance` decision and its header band. **Closed by ADR-040**, which traced that decision to a provably dead operand and deleted the client copy rather than reconciling the formulas, there was no reconciliation to do, because a second model with no authority cannot be argued with.
