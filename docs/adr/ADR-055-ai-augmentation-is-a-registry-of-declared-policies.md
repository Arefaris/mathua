# ADR-055: AI augmentation is a registry of declared policies, not a trusted provider list

*2026-10-16; amended 2026-10-18 and 2026-10-20 before release*

**A learner's study session must not depend on an inference provider, and a learner's data must not reach one whose terms nobody has written down.** That is the whole decision; everything below is what it forced. Mathua now offers two optional features — a product assistant (`POST /api/ai/assistant`) and a goal-scope agent (`POST /api/ai/goal-scope`) that maps a free-text goal to destination ids — behind a registry (`internal/ai`) that decides, per request, which providers may be called. Nothing in it is on the learning critical path: grading, scheduling, mastery and the onboarding fallback are deterministic and stay so, and a disabled registry, an exhausted quota or a provider outage all surface as "unavailable" rather than changing an answer.

**Eligibility is data, not a string.** A provider declares a `Policy` — the most sensitive `DataClass` it may receive, whether its terms permit production learner traffic, whether it is dev-only, and its prompt retention — and that policy is the only thing `Registry.Select` reads. There is deliberately no `"safe"`/`"trial"` enum: that collapses independent facts (who may see data, whether terms allow production, whether prompts may train a model) into one value that can only be wrong in one direction. The zero `Policy` permits public content and denies everything else, so a provider nobody has documented is ineligible for learner data until someone writes the fields down; a policy that permits more than public data with no `Source` is rejected at boot, because a claim without a citation is the shape of an omission. A dev-only provider is inert in production regardless of any flag, so a development setting left set cannot route a real learner to an experimental endpoint.

**Verified 2026-10-15, the production chain is Groq as head and Cloudflare Workers AI as failover**, both declared pseudonymous-and-production with `RetentionNone` — a declaration that, since retention became a field `Select` reads, also has to be confirmed against the account in production (below). Groq's free tier is rate-limited at the *organization* level — one key shares the whole application's budget — which is why a per-identity cap, a global ceiling and a failover provider all exist. Gemini's free tier is disqualified because its terms permit using content to improve Google's products; NVIDIA NIM, Cerebras, OpenRouter's free models and OpenCode Zen are registered dev-only and receive public or synthetic content only. A dev provider with no model id is skipped rather than defaulted, because Mathua has not verified their model ids and inventing one is the failure this registry exists to prevent.

**The assistant is not a tutor, and the first version of this feature was named as if it were.** The endpoint answers "what is Mathua" and "where do I start", and asks one clarifying question when a goal is too vague to map to a place. It was built and shipped as `POST /api/ai/tutor` with a prompt that opened "You are Mathua's study tutor for mathematics", a request body carrying `domain` and `concept_ids`, and a context type carrying per-concept mastery. A tutor answers a maths question; that prompt invited exactly the wrong answer to the question actually being asked, which was a product question. It is now `POST /api/ai/assistant`, the request has one field, and `AssistantContext` carries the public destination catalogue and nothing about a learner. That is also a smaller privacy surface than the version the paragraph below was written for: no mastery, no concept ids, no lesson excerpt ever leaves the server. The endpoint name `/api/ai/tutor` is deliberately left unused rather than repurposed, so a real tutor inside a lesson can take it later without either feature inheriting the other's contract.

**The reply is plain text because the surface that shows it is plain text, and that was a defect too.** The tutor-era prompt said nothing about format, and a live reply came back as `**derivative**` with `\(f(x)\)` and `\[ ... \]` around the maths. The app renders the string as text, so a reader would see the asterisks and backslashes rather than emphasis and a formula. The prompt now states the format it is talking to — plain prose, at most four short sentences, no Markdown, no LaTeX, no lists — and `TestAssistantPromptAsksForPlainProse` fails if that line is removed. A model asked for four sentences also stays inside a budget a free provider will actually serve, which is why the assistant budget dropped from 1500 tokens to 600.

**The assistant is a dock in the corner, and the model never writes a URL.** `components/AssistantDock.tsx` is mounted once in `app/layout.tsx` rather than per page, so a conversation survives navigation. It always renders, and `/api/config` decides what the panel can do rather than whether the control exists: with a provider it answers, and without one it says the assistant is unavailable once and offers the same destinations as links (`/learn`, `/diagnose`, `/plan`, `/graph`, `/glossary`). Hiding it was the earlier behavior and it was wrong for a reason worth recording, because it cost real time: a hidden button makes a switched-off feature indistinguishable from one that was never built, so the same page looked identical whether the assistant was unconfigured, broken or absent, and the cause — no API process on the port the page calls — was invisible from the browser. The panel never fakes an answer and never shows an input that cannot send. Replies arrive as plain prose plus a list of links, and both halves matter: the prompt asks the model to name a destination as `[[id]]`, and `assistantLinks` in `internal/server/ai.go` resolves that id against a table the server owns (`/diagnose`, `/plan`, `/learn`, `/review`, `/graph`, `/glossary`, `/leaderboard`, and the destination catalogue). An id that is not in the table is deleted from the text and produces no link. The href is therefore never a string the model produced, which is what makes this safe against a reply that tries to emit a URL: there is no code path from reply text to an anchor's `href`. Links are deduplicated and capped at four, and a destination link is `/plan?destination=<id>`, which `PlanEditor` now reads as a preselection so the link lands on the thing it named.

**A conversation needs history, and history is where a client gets to write instructions.** The prompt tells the assistant to ask one clarifying question, and a question with no memory of itself is unanswerable, so the request carries `history`. `sanitizeAssistantHistory` keeps the most recent eight turns, accepts only `user` and `assistant` roles, and drops an over-long turn rather than truncating it — so a replayed message is answered as the visitor sent it or not at all. A `system` turn from a client is discarded before it reaches `AssistantContext`, which narrows roles again when it renders messages; either check alone would be enough, and both exist because this is the one field where the visitor supplies content that the model will treat as instruction. `TestAIAssistantHistoryReplaysOnlyConversationTurns` sends a system turn containing an override and asserts no provider ever sees it.

**The assistant request cannot carry an identifier or a graded answer.** `ai.AssistantContext` names `LearnerName`, `LearnerEmail` and `StudentID` as fields *so that* `Messages()` drops them and a test can prove it, and `ExpectedAnswer` is a field for the same reason: a caller holding the answer must hand it over and watch it ignored, rather than be trusted to leave it out. The request reaches the model as `DataPseudonymous` at most, and the test suite asserts a sentinel expected answer never appears in any message a provider receives. This is the same rule the study anchor already follows (ADR-007): the graded answer lives on the server and the client is never given it to forward.

**Quota is two store-backed daily ceilings, and the identities are chosen so they cannot be minted.** An authenticated caller is keyed by `student_id`; everyone else by client IP, because guest ids are generated in the browser and a cap keyed on one is bypassed by clearing `localStorage`. There are two counters because they do different jobs, and the day one request first ran at 1000 requests against a shared free tier made the gap concrete: a per-identity cap bounds one learner and does nothing about many learners at once, which is what actually spends the organization's budget. Both are consumed in one transaction — `ReserveAIUsage` takes a list of `{key, ceiling}` and commits only if every counter is within it — so a request refused by either ceiling leaves *neither* incremented, and two concurrent requests still cannot both read the last free slot. The defaults are 5 per identity and 800 application-wide, the second below the 1000 requests the Groq free tier reports, leaving headroom for retries and the failover leg. The counter lives in a day-scoped `ai_usage` row keyed by an opaque string, not a column on `students`, because a guest has no students row and the guest key is an IP. `ResetProgress` deliberately does **not** clear it (ADR-022): a reset that refilled the daily budget would make the budget meaningless. `DeleteAccount` does clear it, because the account is gone (ADR-026). The cap is correct across replicas only where the store is shared, which is Postgres; a SQLite deployment on one volume counts per machine, so the deployment is either single-machine or Postgres-backed.

**`/api/config` gains one boolean.** `ai_enabled` tells the client whether the features are configured so it can skip the calls; the provider chain, model ids, keys and the per-user quota are operational detail a client has no use for and an attacker does.

**Retention was declared and never read, and a declaration nothing enforces is not a control.** The first version of this registry recorded `Retention` on every policy and then selected on `MaxClass`, production-permitted and dev-only alone. That made `RetentionNone` a comment: a provider that trains on prompts would have been just as eligible as one that keeps nothing. `Select` now reads it, with `RetentionUnknown` treated as the worst case rather than the default — a provider nobody checked is denied anything above public content, so forgetting to verify a provider fails closed instead of opening it. `RetentionTrained` is never eligible for learner data, `RetentionTemporary` reaches pseudonymous but not identifiable, and only `RetentionNone` reaches identifiable data.

**The two defects below were found by reading the provider's own responses, and both would have shipped invisibly.** The rate limiter keyed on the first `X-Forwarded-For` entry, which the client controls — a caller could send `X-Forwarded-For: 1.2.3.4` and be limited under a key of their own choosing (`internal/server/ratelimit.go`). It now reads `Fly-Client-IP` *only when Fly set the deployment's environment* (`FLY_APP_NAME`), or the header named by `AI_TRUSTED_IP_HEADER` for another proxy, and otherwise keys on the socket address. The first fix trusted `Fly-Client-IP` unconditionally, which is correct behind Fly's edge and a bypass anywhere else; because the guest AI quota is keyed by the same function, the bypass was never only a rate limit. And the reasoning-model defect: `openai/gpt-oss-120b` spends part of `max_tokens` on hidden reasoning tokens before it emits anything, so the shipped 200-token goal-scope request spent 135 tokens reasoning and then failed with `json_validate_failed` — while the handler logged it and returned `used_ai:false`, so a feature that never once worked looked like a model with no opinion. It is fixed at both ends. `reasoning_effort: "low"` is sent to Groq (and not to Cloudflare, whose acceptance of the field is unverified), both budgets are 600 tokens, and the adapter no longer reports an empty completion or `finish_reason: "length"` as a reply: both are transient errors the chain can fail over, because a blank answer with a 200 is worse than an honest failure.

**Degradation is announced, not silent.** `POST /api/ai/goal-scope` used to return the same `{destinations: [], used_ai: false}` whether AI was off, the server had no destinations to ground on, every provider had failed, or the model had answered and chosen nothing. Those are four different facts, and a client that cannot tell them apart can only treat them all as "no suggestion", so the response now carries a `reason` — and a provider failure is logged as one rather than swallowed as an empty result.

**Zero-data retention is an account setting, not a policy sentence, so it is confirmed rather than assumed.** Groq's own documentation says ZDR is available and must be switched on; a `Source` that cites the page proves the switch exists, not that anyone flipped it. Since `Select` now trusts `RetentionNone`, production refuses to build a registry containing a production-permitted provider that claims it while `AI_ZDR_CONFIRMED` is unset. The refusal disables AI and reports why (`Settings.DisabledReason`) rather than failing the process: an optional feature misconfigured must leave the deterministic app able to teach.

**Operating it is part of the decision, not an afterthought.** Four things follow from "AI is optional", and each was wrong or absent in the first version. **A prompt must not be able to reach a log.** Provider errors used to keep the raw response body, and a provider that rejects a request commonly echoes pieces of it back — Groq's `json_validate_failed` returns the model's unparsed generation under `failed_generation`, which in an assistant whose entire input is the visitor's words can restate them. Only the provider's own `error.message` now survives, with control characters stripped (so a crafted message cannot forge a second log line) and the length bounded; the body itself is dropped. **Failover must not outlive the response.** The per-attempt timeout and the number of providers together bounded a request at 60 seconds, twice the server's `WriteTimeout`, so a slow head plus a slow failover could have the connection cut mid-write — a dropped connection, which no client can fall back from. Each attempt is now capped at 12 seconds and the whole chain at 25, under the write deadline, and reaching the chain deadline returns an error rather than pretending there is budget left. **The counter table must be pruned.** `ai_usage` rows are day-scoped and a passed day can never be reserved again, so the janitor deletes everything older than 42 days, computed from the clock rather than from a request so a replica whose clock is a day behind cannot delete a day another replica is still spending. **A rate nobody can total is not a number.** The server now counts requests, successes, failovers, denials and fallbacks and logs one line of integers on the janitor tick. They are deliberately not on an HTTP endpoint: `/api/config` answers the client, and provider health and quota consumption are operational detail a client has no use for and an attacker does. A denial is counted separately because it is the one AI outcome no provider ever sees.

**Rollout is staged, and the first stage is the one that matters.** Because `AI_ENABLED` defaults off, the whole change is inert until an operator turns it on, which is what makes the order below safe rather than merely careful.

1. **Deploy with `AI_ENABLED` unset.** `/api/config` must report `ai_enabled: false` and both endpoints must answer "unavailable". This proves the one irreversible part — the `ai_usage` schema addition — migrated, and that nothing on the deterministic path moved.
2. **Development, dev providers, a throwaway key.** Confirm the prompt shape and that the quota counters move, without sending a learner's words anywhere real.
3. **Production, one provider, small caps.** Groq only, `AI_GLOBAL_DAILY_CAP=50` and `AI_DAILY_USER_CAP=3`. Confirm `ai_enabled: true`, that a real assistant reply arrives, that the same identity is refused at the cap, and that the boot line reports the caps it configured. This stage cannot run unconfirmed: with `AI_ZDR_CONFIRMED` unset in production the registry refuses to build, AI stays off, and the boot log says why.
4. **Raise the global cap** to the intended 800 once a day of counters shows the failure and denial rates are what the caps were sized for.

**Rollback is one variable.** Setting `AI_ENABLED=false` (or removing it) restores the previous behavior exactly, because nothing on the learning path ever consulted the registry: grading, scheduling, mastery and the onboarding match are the same code they were. The `ai_usage` table is additive and its rows expire through the janitor, so no migration has to be reversed. If a provider fails, the chain fails over and then reports unavailable — a learner is never blocked by it.

**Two things are still unverified and must be checked before step 3, not during it.** The Cloudflare failover leg has never been called with a real credential: its base path and `@cf/...` model id are declared but unproven, so the chain has only ever had one working leg. And the production database is either Postgres or a single SQLite machine: the daily ceilings are exact across replicas only where the store is shared, so a second machine behind SQLite silently doubles every cap. Both are configuration facts this ADR can state and neither can settle.

**Consent, age and data-subject scope are still open.** The two features send a learner's typed words to a third-party inference provider. The code bounds what that can be — no identifier, no graded answer, no learner record — but whether a learner (or a minor's guardian) is asked, and what the privacy notice says, is a product and legal decision this ADR does not make and which must be recorded before real learner traffic reaches the endpoint. The gate that exists today is technical: `AI_ENABLED` defaults off, and production additionally requires the zero-retention confirmation above.
